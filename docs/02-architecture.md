# 技術架構（STEP 3）

版本：草案 v0.1（2026-11-10），待你確認後才開始 STEP 4。

## 1. 技術選擇

| 層 | 選擇 | 理由 |
|---|---|---|
| 語言 | TypeScript（strict） | 引擎、伺服器、前端共用同一套型別 |
| 套件管理 | npm workspaces | 電腦已有 npm 11，不需要額外安裝工具 |
| 遊戲引擎 | 純 TypeScript，**零執行期依賴** | 可在伺服器、瀏覽器、測試三處運行 |
| 前端 | React + Vite | 你建議的組合，本機環境適用 |
| 後端 | Node.js 24 + `ws`（WebSocket） | 輕量，足夠應付雙人房間 |
| 資料庫（開發） | SQLite，使用 Node 內建的 `node:sqlite` | 已確認本機可用，不需要編譯原生模組 |
| 資料庫（正式） | PostgreSQL | 經資料存取層抽象，日後才切換 |
| 單元／整合測試 | Vitest + fast-check（隨機性質測試） | 性質測試用來自動找卡牌數量異常等問題 |
| 端對端測試 | Playwright | 可同時開兩個瀏覽器模擬真正的雙人連線 |

沒有採用的東西：遊戲框架（Phaser 等，卡牌遊戲用 DOM 及 CSS 動畫已足夠）、ORM（資料表很少）、Redis（單一伺服器不需要）、微服務。

## 3. 遊戲引擎

### 3.1 設計原則

1. **確定性**：同一個種子加同一串玩家決定，必定得到相同結果。亂數只來自引擎內的種子產生器，種子只存在伺服器。
2. **狀態是唯一事實**：UI 顯示的所有數字都由狀態計算出來，沒有另外儲存的 Level、Stock 數字。
3. **引擎只會問問題**：引擎運行到需要玩家決定時就停下，回傳一個「待決定事項」；收到合法答案才繼續。沒有任何路徑可以在玩家未選擇時繼續。
4. **所有卡牌移動經同一個函數**：這是插入型規則處理、區域移動觸發、重播紀錄的唯一入口。

### 3.2 對外介面

```ts
createGame(config, seed): GameState
getPendingDecision(state): Decision | null     // 現在輪到誰決定甚麼
getLegalChoices(state): Choice[]               // 所有合法答案
applyChoice(state, playerId, choice): { state, events }
getPlayerView(state, playerId): PlayerView     // 已過濾隱藏資訊
```

`applyChoice` 收到不在 `getLegalChoices` 內的答案時會拒絕並保持原狀態。伺服器、AI、測試、重播全部只用這五個函數。

### 3.3 狀態模型

- 每張實體卡有固定的 `instanceId`（一局 100 張），另有 `zoneEntryId`：每次由枠移到枠以外的區域就換新，用來實現「視為新卡」（CR-3.1.4）及最終資訊（CR-8.11）。
- 區域：每名玩家有山札、手牌、控え室、Clock、Level、Stock、Climax、思い出、解決領域、5 個枠、5 個 Marker 置場。
- 流程堆疊：記錄目前的階段、步驟及步驟內的進度。
- 待機自動能力清單（CR-8.7.2）。
- 持續效果清單，每項有來源、期限、時間戳。
- 回合內計數器（回合次數限制、是否第一次宣告步驟等）。

### 3.4 流程控制

流程是一個明確的狀態機，階段及步驟與官方第 6、7 章一一對應。兩個核心程序：

**Check Timing（CR-8.5.1）**

```
重複：
  執行所有檢查型規則處理（同時），直到沒有新的
  若回合玩家有待機能力 → 讓他選一個 → Play 並解決 → 重新開始
  若非回合玩家有待機能力 → 讓他選一個 → Play 並解決 → 重新開始
  否則結束
```

**原子移動（所有卡牌移動的唯一入口）**

```
移動卡牌
  → 記錄事件（供觸發及重播）
  → 檢查觸發條件，符合的能力加入待機清單
  → 若不是在支付 Cost：
       山札為 0 → 執行 Refresh（CR-9.2）
       Clock ≥ 7 → 執行 Level Up（CR-9.3）
  → 若正在支付 Cost：延後到支付完成（CR-8.4.2.1）
```

這個設計直接對應官方的「插入型」與「檢查型」區分，避免傷害途中 Refresh 之類的次序錯誤。

### 3.5 防止無限循環

- 官方的循環規則（CR-11.1）會實作：引擎偵測到完全相同的狀態重複出現時，按三種情況處理。
- 另設工程保險：單一 Check Timing 內解決的能力數量有上限（例如 500）。超過即中止對局、保存重播並記錄為引擎錯誤。這只是保險，不是規則。

## 4. 卡牌能力引擎

### 4.1 卡牌能力是資料，不是程式

每張卡的能力以結構化資料描述，由同一個直譯器執行。新增卡牌不需要改引擎；只有遇到全新的效果原語時才需要擴充直譯器。

```jsonc
{
  "type": "AUTO",
  "trigger": { "event": "ATTACK_DECLARED", "subject": "SELF" },
  "condition": { "climaxAreaHasName": "…" },
  "cost": [{ "op": "PAY_STOCK", "n": 1 }],
  "optional": true,
  "effect": [
    { "op": "SEARCH_DECK", "filter": { "anyTrait": ["…", "…"], "kind": "CHARACTER" },
      "upTo": 1, "reveal": true, "to": "HAND" },
    { "op": "SHUFFLE_DECK" }
  ]
}
```

以上是按官方卡表實際存在的 SAO/S20-001 第二個能力的結構示意，欄位名稱到 STEP 4 才定案。

### 4.2 組成部分

| 部分 | 內容 |
|---|---|
| 觸發事件 | 區域移動、階段及步驟開始、攻擊宣告、Reverse、傷害被 Cancel、「使用了某關鍵字」等 |
| 條件 | Level、經驗（Level 置場內容）、記憶（思い出內容）、特徵、卡名、狀態、位置、Climax 置場內容、回合歸屬 |
| Cost | 支付 Stock、Rest、棄手牌、放 Clock、送思い出、公開手牌等，按文字次序執行 |
| 效果原語 | 抽牌、棄牌、搜尋、回收、洗牌、公開、移動、Stand／Rest／Reverse、增減 Power／Soul／Level、給予能力、給予傷害、置換、建立延遲觸發 |
| 目標選擇 | 「選 N」及「選最多 N」的義務差異（CR-8.6.3.1）由直譯器統一處理 |
| 期限 | 回合結束前、對手回合結束前、永續、本局 |

### 4.3 處理次序

1. 宣告 → 2. 檢查顏色及 Level 條件、使用時機 → 3. 作出選擇 → 4. 確認並支付全部 Cost → 5.「已 Play」事件 → 6. 解決效果（期間觸發的能力只會待機，不會插隊）→ 7. Check Timing → 8. 回到正常流程。

這是 CR-8.6.2 及 CR-8.5 的直接實作。

### 4.4 持續效果及數值計算

Power、Soul、Level、特徵、能力等「現在的值」不會儲存，每次由印刷值按 CR-8.9.1 的五層次序重新計算，避免效果互相覆蓋或殘留。

### 4.5 核實狀態

每個能力資料都有 `verification` 欄位：

| 值 | 意思 | 可否用於對戰 |
|---|---|---|
| `verified` | 已對照官方原文、エラッタ及 Q&A，並有通過的測試 | 可以 |
| `pending` | 已編寫但未完成核實或測試 | 只限測試模式 |
| `unsupported` | 未確認 — 暫不支援自動執行 | 不可以；含有這類卡的卡組不能開始對戰 |

每張卡也會記錄官方原文的雜湊值。官方修改文字（エラッタ）後雜湊不符，該卡自動降回 `pending`。

## 5. 卡牌資料庫

- **來源檔是 JSON**（每個系列一個資料夾），放在 Git 及 iCloud 內。SQLite 只是啟動時由 JSON 建立的搜尋索引，可隨時刪除重建。
- 每張卡的欄位：卡號、日文名、讀音、英文名（如有）、中文名（如有可靠來源）、種類、顏色、Level、Cost、Power、Soul、特徵、Trigger、稀有度、Title、商品、發售日、**官方原文**、**中文解釋（獨立欄位，附來源類別）**、エラッタ紀錄、官方 Q&A 連結、限制、能力資料、核實狀態。
- 中文解釋的來源類別分為：官方文字／官方規則／官方 Q&A／社群解釋／AI 輔助說明。介面會用不同標籤顯示，AI 輔助說明一律標示「非官方」。
- **圖片獨立處理**：卡牌資料只存 `imageKey`。圖片由 `ImageProvider` 介面提供，可切換：
  1. 佔位圖提供者（預設）：按卡牌資料即時繪製的卡框，顯示卡名、數值及圖示，不含官方美術。
  2. 官方連結提供者：不顯示圖片，只提供「在官方卡表查看」的連結。
  3. 本機資料夾提供者：讀取使用者自行放在 `card-assets/local.nosync/` 的圖片。
  更換提供者不影響任何規則程式碼。

## 6. 多人連線

```
瀏覽器 A ──WebSocket──┐
                      ├── 伺服器（房間 → 引擎實例 → 狀態儲存）
瀏覽器 B ──WebSocket──┘
```

- **伺服器權威**：引擎只在伺服器運行。客戶端只送出「我選這個答案」，只收到自己的 `PlayerView` 及事件。客戶端沒有完整狀態，所以看不到對手手牌、山札次序及 Stock 內容。
- **房間**：6 位房間代碼及邀請連結；上限 2 人；準備 → 開始 → 結果 → 再戰。
- **防重複提交**：每個決定事項有唯一 `decisionId`。伺服器只接受對應目前 `decisionId` 的第一個答案，重複或過期的一律忽略。
- **重新連線**：每名玩家有存在瀏覽器的重連憑證。重連後伺服器發送目前的完整視圖。
- **持久化**：每個行動之後把行動紀錄寫入 SQLite。伺服器重啟時由種子及行動紀錄重建對局（靠引擎的確定性）。
- **斷線處理**：保留房間一段時間（預設 10 分鐘，可設定），逾時判負。這是平台規則，不是 WS 規則，會在介面清楚說明。

### 部署（STEP 9 才需要決定）

跨裝置、跨網絡對戰需要一部雙方都連得到的伺服器。只在這部 Mac 運行的話，只有同一個 Wi-Fi 內的裝置可以連線。選項：

| 選項 | 適合 | 費用 |
|---|---|---|
| 同一 Wi-Fi | 開發及測試 | 無 |
| 通道服務（例如 Cloudflare Tunnel） | 與朋友測試，Mac 要保持開機 | 免費 |
| 雲端主機 | 長期運作 | 每月數美元起 |

公開部署會提高版權風險，見 [03-phase1-plan.md](03-phase1-plan.md)。

## 7. AI

- AI 在伺服器運行，但**只能取得 `PlayerView` 及 `getLegalChoices`**，與真人玩家完全相同。`ai/` 套件在程式層面不能引入引擎的內部狀態模組，由 lint 規則強制執行。
- AI 只能從合法答案中選一個，所以不可能作出非法行動、多用 Stock 或無視 Cost。

| 難度 | 方法 |
|---|---|
| Beginner | 規則式：能出就出、能攻就攻，隨機選合法目標 |
| Normal | 評分函數：手牌、Stock、Clock、Level、場面 Power；按 Power 及 Soul 選擇攻擊方式 |
| Advanced | 加入：Climax 配合、剩餘 Climax 數量推算（只用公開資訊）、Cancel 機率、攻擊次序 |
| Expert | 資訊集蒙地卡羅：按已知公開資訊隨機補上未知部分，模擬多次後選擇期望值最高的行動；加入終局斬殺計算 |

遇到 `unsupported` 的卡：這類卡本來就不能進入對戰。如果 AI 對某個決定沒有評分依據，會選擇預設的安全選項（優先「不發動可選效果」），並寫入日誌。

## 8. 重播

每個行動記錄：行動編號、玩家、類型、相關卡、行動前後的狀態雜湊、觸發的能力、結果、時間戳。完整的前後狀態不逐一儲存，而是由種子及行動序列重算；需要時可在任何一步展開完整狀態。測試可直接比對預期狀態與實際狀態。

重播檔含有種子，對局結束後才可下載，避免洩漏山札次序。

## 9. 測試策略

| 層次 | 工具 | 內容 |
|---|---|---|
| 規則單元測試 | Vitest | 規則登記表的每一條至少一個測試，測試名稱含 Rule ID |
| 情境測試 | Vitest + 自製情境建構器 | 直接指定各區域內容，執行行動，比對結果。用於 Refresh、傷害途中耗盡山札等邊界情況 |
| 卡牌測試 | Vitest | 每張 `verified` 的卡至少一個測試，覆蓋其所有能力 |
| 性質測試 | fast-check | 隨機合法行動打完整局數千次，每一步檢查全域不變量（50 張守恆、無重複、無資訊洩漏、確定性） |
| 整合測試 | Vitest | 兩個 AI 用真實卡組由開局打到分出勝負 |
| 連線測試 | Playwright | 兩個瀏覽器進入同一房間；重新整理、斷線重連、重複提交 |
| 覆蓋檢查 | 自製腳本 | 登記表有規則沒有測試、或有 `verified` 卡沒有測試時，令測試失敗 |

## 10. 前端

- React + Vite，手機優先的自適應佈局。
- 介面完全由 `PlayerView` 及事件驅動，不含任何規則判斷。可選的行動來自伺服器提供的合法選項。
- 動畫以事件為單位排隊播放（CSS transform），不影響狀態。
- 點擊任何術語顯示繁中解釋，資料來自術語表及規則登記表。
- 不使用任何官方 UI 素材。

## 11. 開發原則

- 引擎在前、UI 在後。STEP 4 至 6 期間沒有畫面，只用測試及文字輸出驗證。
- 任何規則有疑問時，先查官方資料並記錄在 `rules/` 內，然後才寫程式。
- 不留假的完成項目：未完成的功能在登記表及卡牌資料上如實標示。
